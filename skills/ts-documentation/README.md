# ドキュメントスキル

JavaScript/TypeScript のドキュメントを日本語で監査・改善するためのスキル。JSDoc、コメントマーカー、アンチパターン、判断基準を扱う。

## 設計方針

このスキルは **必要なときだけ起動されること** と **実装文脈に応じた判断** を重視する。

1. **明確な起動条件** - `@param`, `@returns`, `@template`, `@example`, `JSDoc`, `TODO`, `FIXME` などの具体語で起動される。
2. **アンチパターン** - よくある誤りを修正例付きで示す。
3. **判断フレームワーク** - public API と内部コードを分けて扱う。
4. **充足度確認** - 関数、型、interface、class、定数ごとの確認項目を持つ。
5. **特殊ケース** - deprecated API、overload、generic、callback、builder、event を扱う。
6. **衝突時の解決** - 詳細さと簡潔さが衝突したときの優先順位を示す。

## 対象範囲

### JSDoc 監査

- エクスポートされたコードと内部コードの基準分け
- 関数、型、interface、class、定数の文書化
- ジェネリック型パラメータの `@template`
- オブジェクトパラメータの dot notation
- 言語指定付き `@example` コードフェンス
- エラー条件の `@throws`

### コメント品質

- `TODO`, `FIXME`, `HACK`, `NOTE`, `PERF`, `REVIEW`, `DEBUG`, `REMARK`
- 削除するコメントの判断
- 保持するコメントの判断
- コメント配置の改善

### 判断支援

- 誤り/正しい例
- 監査時の考え方
- ドキュメント充足度の判断
- 判断が衝突したときの優先順位
- deprecated API、overload、callback などの特殊ケース

## 使い方

### 呼び出し例

このスキルは次のような依頼で使う。

```text
src/utils/math.ts のドキュメントを監査してください
```

```text
src/api/client.ts のエクスポートされた関数に JSDoc を追加してください
```

```text
この関数に @param と @returns を追加してください
```

```text
コメントをレビューして TODO/FIXME マーカーを適切にしてください
```

```text
@example 付きでこの関数を文書化してください
```

```text
src/core/ のコメントを修正し、不要コードを削除して配置を改善してください
```

## 動作の流れ

### 起動と読み込み

1. **現在の構成を確認** - `SKILL.md` を読んで構成を把握する。
2. **必要な参照資料を読む**:
   - `references/jsdoc.md` - JSDoc の構文とタグ要件
   - `references/comments.md` - TODO/FIXME マーカー、削除/保持、配置
3. **監査ワークフローを適用** - public/internal の二段階ルールと判断基準を使う。

### 監査手順

**手順 1: 対象範囲を決める**
- エクスポートされたコードか。public API なら包括的なドキュメントが必要。
- 内部コードか。判断基準を適用する。

**手順 2: 充足度を確認する**
- 関数、型、class、定数ごとの確認項目を使う。
- `@param`, `@returns`, `@template`, `@throws`, `@example` の不足を確認する。

**手順 3: 構文を検証する**
- `@example` は言語指定付きコードフェンスを使う。
- オブジェクトパラメータは dot notation を使う。
- `void` 関数には `@returns` を付けない。
- ジェネリックには `@template` を付ける。

**手順 4: コメントをレビューする**
- マーカーを適切に使う。
- 不要コードと編集履歴を削除する。
- ツールディレクティブとビジネスロジックのコメントを保持する。
- 行末コメントを対象コードの直前へ移動する。

**手順 5: 検出結果を報告する**
- `file:line` 付きで報告する。
- 問題種別ごとに分類する。
- 具体的で実行可能な修正案を出す。

## 主な機能

### アンチパターン

- コードフェンスのない `@example`
- 内部コードの過剰な文書化と public API の不足
- コメントアウトされたコードの放置
- WHAT/WHY ではなく HOW を書く JSDoc
- `void` 関数の `@returns`
- 文脈のない `TODO`

### 判断フレームワーク

**二段階アプローチ:**
- Public API: 常に包括的に書く。
- 内部コード: 複雑さ、保守コスト、価値とノイズを比較して判断する。

### 判断基準

次の対象ごとに充足度を確認する。
- 関数/メソッド
- 型/interface
- クラス
- 定数/変数

### 判断が衝突したときの扱い

- public API は詳しく、内部コードは必要十分にする。
- WHAT/WHY を優先し、HOW は実装コメントに寄せる。
- 既存コードベースの一貫性を優先する。

### 特殊ケース

- `@deprecated`, `@see`, 移行パス
- オーバーロード関数
- ジェネリックユーティリティ型
- コールバックパラメータ
- ビルダーパターン
- イベントエミッター

## 組み込み方針

このスキルは次の場合に使う。

- ドキュメント監査が主目的
- 何をどこまで文書化するか判断が必要
- エクスポートされた関数/型/クラスに JSDoc を追加する
- コメント品質とマーカーをレビューする
- deprecated、overload、generic などの特殊ケースを扱う

## スキル情報

- **規模**: 約 300 行 (`SKILL.md`)
- **知識の構成**: 専門的なガイダンス / 起動条件 / 参照資料へのナビゲーション
- **構成パターン**: 軽量なナビゲーションと詳細な参照資料の組み合わせ
