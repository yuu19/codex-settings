# `natural-japanese` 校正ゲート

技術記事の日本語本文を変更した後、独立した校正subagentに `natural-japanese` を使わせる。subagentはレビューだけを行い、記事ファイルは変更しない。親の `blog-article-creator` が指摘を判断し、記事を編集して技術的な不変条件を再確認する。

## 責務

- `natural-japanese`: 日本語の自然さ、語順、読点、一文一義、文長、リズム、AI臭さを判断する。
- `blog-article-creator`: frontmatter、技術構成、コード、コマンド、数式、数値、用語、画像、リンク、引用、Zenn記法を管理する。
- 校正subagent: 構造化した指摘を返す。ファイルを変更しない。
- 親: 指摘を判断台帳へ統合し、「直す」か「残す（理由）」を決めて変更する。

短さ自体を目的にしない。事実、主述、係り受け、技術的な意味を保った候補の中でのみ、簡潔さを判断材料にする。lintのseverityは疑いの強さであり、修正義務へ直接変換しない。

## 起動条件と範囲

日本語の文を作成、削除、または意味・構造・言い回しの面で実質的に変更したら校正を起動する。一文だけの変更でも実質的なら対象にする。誤字、句読点、リンク、コード識別子だけの機械的変更では省略できる。タイトルやdescriptionだけの変更も、機械的で意味を変えない場合は省略できる。英語、コード、画像、デプロイだけの変更も対象外とする。

既存記事では、subagentは記事全体を読んで文脈とlint結果を確認するが、修正提案は変更箇所と、その変更が原因で生じた前後の接続問題に限定する。既存の範囲外問題は、重大な場合だけ残課題として報告する。新規記事またはユーザーが記事全体の校正を明示した場合は、記事全体を変更可能範囲とする。

本文校正を起動したときは、タイトル、description、見出し、alt text、キャプションも目視する。lintはYAML frontmatterなどをマスクするため、タイトルとdescriptionをlint結果だけで確認しない。subagentはfrontmatterのキー、形式、公開フラグを変更対象にしない。

## モード選択

通常はquickを使う。記事が公開予定であることや、`blog_published`、`published`の値だけを理由にfullへ切り替えない。

次のいずれかではfullを使う。

- ユーザーが徹底的、しっかり、時間をかけた校正を求めた。
- 日本語本文が目安として1万字を超える。
- 医療、法律、金融、セキュリティなど、表現の誤りが重大な判断へ影響する。
- 企業や個人への評価、強い批判など、評判上の影響が大きい。

fullを始める前に、`natural-japanese`に記載された所要時間の目安をユーザーへ伝える。

## custom agentの選択

校正には`~/.codex/agents`へ導入された次のcustom agentを使う。モデル、推論強度、sandbox、役割の指示は各agent TOMLを正本とし、このreferenceから起動時に上書きしない。再レビューでは同じsubagentを再利用する。

| モード | 構造 | 読みやすさ | 技術ブログ適合 |
| --- | --- | --- | --- |
| quick | `quick_proofreader` | - | - |
| full | `structure_reviewer` | `readability_reviewer` | `blog_fit_reviewer` |
| 最高品質のfull | `structure_reviewer_max` | `readability_reviewer_max` | `blog_fit_reviewer_max` |

起動時は`fork_turns: none`として会話履歴を引き継がない。代わりに、親は記事本文、変更範囲、変更目的、守るべき技術用語、関連するlint・outline・termsの出力を明示的に渡す。記事に不要な会話や別タスクの情報は渡さない。

ユーザーが「最高品質」「最大」など、品質を最優先したfull校正を明示した場合に限り、名前が`_max`で終わる3つのagentを使う。通常のfull校正では`_max`のないagentを使う。

指定したcustom agentを利用できない場合、ユーザーが構成を明示していなければ、同じ役割の一時subagentへ縮退して校正を続け、完了報告に縮退内容を記載する。ユーザーがagent、モデル、または推論強度を明示した場合は、無断で代替せず、校正を完了扱いにしない。

## quick

1. 親はcustom agent `quick_proofreader`を起動し、記事ファイル、変更箇所、変更目的、守るべき技術用語を渡す。
2. subagentは `natural-japanese` の `SKILL.md` を読み、子subagentを起動せずquickとして作業する。
3. subagentはskillディレクトリを基準に、`uv run scripts/lint.py --json --genre tech <記事>`を実行し、記事全体をスケルトン通読する。
4. subagentは指摘だけを返し、親が判断台帳へ統合して記事を変更する。
5. 親は同じsubagentへ再レビューを依頼する。すべての指摘が「直した」か「残す（理由）」に仕分けられ、新しい指摘がなくなるまで続ける。

## full

fullでは、校正用の中間subagentを置かない。親が調整役となり、利用可能な並列枠の中で選択した3つのcustom agentを直接起動する。以下は通常のfullで使うagent名であり、最高品質のfullでは対応する`_max` agentへ置き換える。

1. `structure_reviewer`: 見出しと段落の流れ、主メッセージ、濃淡、反復を確認する。
2. `readability_reviewer`: 語順、読点、一文一義、主述の距離、冗長さ、リズムを確認する。
3. `blog_fit_reviewer`: 想定読者、記事の目的、導入と結び、過剰な演出、一般論、技術記事固有の構成を確認する。既存のreportやmemoのdoctypeを無理に当てない。

親は最初に、`natural-japanese`のskillディレクトリを基準として、次を一度だけ実行する。

```bash
uv run scripts/lint.py --json --genre tech <記事>
uv run scripts/outline.py --json <記事>
uv run scripts/terms.py --json <記事>
```

記事、変更範囲、目的、守るべき用語と、これらの出力を3つのsubagentへ共有する。subagentは記事を変更せず、所見を返す。親は指摘を統合して記事を変更し、変更が影響した観点の同じsubagentへ中間再レビューを依頼する。見出し移動や段落再構成など広い変更では3つすべてへ戻す。

lintと判断台帳が収束した最終候補は、3つすべての同じsubagentが再確認する。新しい指摘があれば台帳へ追加して収束を続ける。

## 指摘と収束

subagentは重大な読者影響から順に、指摘ごとに次を返す。

- 対象位置
- 問題の分類
- 読者への影響
- 修正案
- 意味や技術的正確性を損なうリスク
- lint由来か目視由来か

親は `natural-japanese` の判断台帳に、各指摘を「直した」または「残す（理由）」として記録する。同じ指摘が2回続けて再発した場合は、理由を付けて残すか、言い換えではなく文・段落の構造から直す。回数だけを理由に未判断の指摘を捨てない。

修正後は親がlintをbaseline付きで再実行し、resolved、new、persistingを確認する。台帳上の全指摘が仕分けられ、修正が新しい指摘を生んでいない状態を収束とする。

## 技術的な再検証

校正を反映した後、親は差分を読み、次を再確認する。

- frontmatterのキー、形式、公開フラグ
- コードブロック、コマンド、出力例
- 数式、数値、単位、否定表現
- API名、識別子、固有名詞、専門用語
- URL、引用、出典
- Zenn固有記法

対象リポジトリに記事検証コマンドがあれば実行する。ビルドやデプロイは、ユーザーが依頼した場合または対象リポジトリの規約が必須としている場合だけ実行する。

## 実行できない場合

`natural-japanese`、校正subagent、lintのいずれかを利用できない通常の記事作業では、親が手動校正へ切り替える。skillを読める場合は同skillの手動チェックリストを使い、skill自体を読めない場合は、このreferenceにある責務、起動範囲、指摘、技術的な再検証の観点を手動で確認する。完了報告では、機械検査または独立レビューを実施できなかったと明示する。この縮退時も記事作業は完了できる。

ユーザーが `natural-japanese` による校正を明示的に求めた場合は、skill、校正subagent、必須検査のいずれかを利用できなければ完了扱いにしない。実施していない校正を通過したと報告しない。

## 完了報告と後片付け

完了報告には、quick/fullの別、使用したモデルと推論強度、lintと目視レビューの結果、修正件数、理由付きで残した件数、縮退の有無、ユーザー判断が必要な残課題を簡潔に示す。判断台帳の全件は通常掲載しない。

判断台帳、lint、outline、termsのJSON、途中版などの中間ファイルは一時領域だけに置き、校正が収束したら削除する。完成記事と、ユーザーが明示的に求めた成果物だけをリポジトリに残す。
